# miniproto v1 Implementation Plan

## Summary

- Start from clean `master`; create `codex/v1` only after plan approval. The first approved action is writing this plan to `PLAN.md`, not implementing code.
- Build v1 as an async-first Python 3.13+ reusable MTProto engine and SDK with a mandatory bundled Rust/PyO3 extension for crypto and TL hot paths, plus pure Python fallbacks for source builds/tests. This directly answers Pyroblack/Hydrogram's speedup lesson: native acceleration must be built in, not an optional afterthought.
- Use `uv`, `ruff`, and `ty` for Python; use Cargo, `cargo fmt`, `clippy`, and `maturin` for Rust/Python packaging.
- Target production-grade core MTProto: authorization, encrypted sessions, generated raw API, TCP transports, retries/reconnects, ordered updates, text messages, media upload/download, docs, CI, and wheels.
- Exclude stars, webapps, admin/business helpers, payments, secret chats, calls, stories helpers, and framework-level bot abstractions from v1 unless needed to keep raw API compatibility. Routers, filters, decorators, middleware, plugins, conversation helpers, and broad high-level Telegram framework behavior belong in `mpgram`, not `miniproto`.

## Key Changes

- Repository setup: add `pyproject.toml`, `uv.lock`, `Cargo.toml`, `rust/miniproto/`, `src/miniproto/`, `tools/schema/`, `tests/`, `docs/`, `.github/workflows/ci.yml`, `.gitignore`, `CONTRIBUTING.md`, `SECURITY.md`, `CHANGELOG.md`, and `PLAN.md`.
- Packaging: use `maturin` as the Python build backend; expose Python modules from `src/miniproto` and the native extension as `miniproto._native`; ship regular and free-threaded CPython wheels where supported; publish one synchronized Cargo source package for accelerator provenance and version parity without promising a standalone Rust API in `0.1.x`.
- Public API: expose `Client`, `ClientConfig`, `TransportConfig`, `DeviceInfo`, `SessionStorage`, `EncryptedSQLiteSessionStorage`, `InMemorySessionStorage`, `Peer`, `Message`, `Media`, `Update`, `NewMessage`, `QuickAckReceipt`, `RpcError`, `FloodWait`, `Unauthorized`, and generated `miniproto.raw.functions` / `miniproto.raw.types`.
- Client API: implement `async with Client(...)`, `connect()`, `disconnect()`, `is_authorized()`, `sign_in_phone(phone, code_callback, password_callback=None)`, `sign_in_bot(token)`, `get_me()`, `resolve_peer(peer)`, `send_message(peer, text, ...)`, `send_file(peer, file, ...)`, `download_media(media, destination, ...)`, `iter_updates()`, `on(NewMessage, handler)`, and `invoke(raw_request)`; `invoke()`, `send_message()`, and final file-send submission expose default-off quick-ACK callbacks without changing RPC completion semantics.
- Schema/codegen: treat generation as a first-class subsystem; pin TDLib as canonical structure, Telegram Desktop as the validated layer source, and core schema/error/changelog inputs as independent documentation and drift evidence with per-source URL, byte count, fetch date, and SHA-256; generate deterministic typed dataclasses, serializers, deserializers, RPC error mappings, docs stubs, source comparisons, offline stale-generation CI, and scheduled network freshness reports.
- Runtime architecture: follow the useful Pyrogram-family layout without inheriting LGPL/GPL code: separate `connection`, `crypto`, `session`, `storage`, `raw`, `types`, `methods`, `dispatcher`, and `errors`, but keep v1 smaller than Pyroblack/Hydrogram by exposing raw escape hatches instead of implementing every high-level feature. Do not add framework primitives such as routers, filters, middleware, plugins, or decorator-first application lifecycles to `miniproto`; those are `mpgram` responsibilities.
- Protocol core: implement MTProto 2.0 only; support auth key generation, RSA padding, DH exchange, AES-IGE encryption, msg_key derivation, salt management, monotonic msg_id generation, seq_no rules, containers, gzip payloads, ordinary acks, opt-in transport quick ACK, ping/pong, bad salt/msg recovery, RPC response correlation, reconnects, and bounded retry policy.
- Transport: default to TCP abridged; implement TCP intermediate and real padded intermediate behind config; use stateful native/fallback chunk pumps for fragmented/coalesced frames, payload/quick-ACK/error events, bounded retained buffers, and multi-frame drain while Python asyncio retains socket/reconnect ownership; support IPv4/IPv6 DC options, DC migration, export/import authorization, connection pools for media, proxy hooks, deadlines, and backpressure.
- Performance: ship Rust implementations for AES-256-IGE, AES-CTR, AES-CBC, key derivation, XOR, fast TL primitive encode/decode, `pq` factorization, transport framing, and a generated reviewed 30-constructor Layer 228 TL hot set; offload pack/unpack and media crypto to executor-friendly native calls while keeping exact Python fallbacks; add `uvloop` on supported Linux/macOS CPython and `winloop` on Windows CPython.
- Session/reconnect: adopt Pyroblack's concrete lessons: explicit start/stop/restart locks, duplicate msg_id tracking, bounded pending ack batching, ping-delay-disconnect keepalive, reconnect throttling, and clear handling for auth-key-not-found / invalid DC / transport flood.
- Updates: persist `pts`, `qts`, `seq`, and date; implement `updates.getState` / `updates.getDifference`; normalize short updates; recover gaps before emitting events; never emit duplicates after reconnect; expose bounded update queues with configurable overflow behavior.
- Storage/security: default `ClientConfig` to encrypted SQLite at the relative `miniproto.session.sqlite` path, requiring a user-provided key or `MINIPROTO_SESSION_KEY` before any session artifact is created; persist auth keys, DC options, user identity, update state, and peer access hashes; require explicit `InMemorySessionStorage` for ephemeral use; redact api_hash, phone, auth_key, session key, bot token, 2FA values, and proxy credentials from logs.
- Media/messages: implement text send/edit/delete basics, plain text and Markdown-lite entities, `messages.sendMessage`, small/big upload paths, 512KB default chunks, concurrent upload queues, streamed upload for unknown-size files, resumable download, one ordered streaming `iter_download()` engine, shared cancellation-safe byte-weighted schedulers per DC and direction, optional plain `upload.getFileHashes` verification, mandatory CDN redirect/decryption/hash verification, progress callbacks, and flood-wait handling.
- Observability: use stdlib `logging` with structured `extra`; expose counters/hooks for bytes sent/received, RPC latency, reconnects, flood waits, update gaps, queue depth, and upload/download throughput; no telemetry by default.
- Documentation: add install, quickstart, auth, session security, raw API, updates, media, production deployment, Telegram ToS/API warning, migration-from-Pyrogram/Telethon notes, speedups/native-extension notes, runnable examples, a committed searchable Astro/Pagefind site, base-safe GitHub Pages publication, and a lean unprivileged Alpine image for root-hosted VPS deployment.

## Package Boundary

- `miniproto` is the reusable MTProto protocol engine and SDK for Python. It owns protocol correctness, generated raw API access, sessions, transport, auth, RPC correlation, updates, peer/access-hash handling, media primitives, observability hooks, and a small high-level surface that proves the core works.
- The bundled Rust crate is named `miniproto` because the crates.io name is reserved for this project, but its current role is still the native acceleration layer for the Python package. The Python extension module remains `miniproto._native`.
- `mpgram` is the separate high-level Telegram application framework package. It is cloned as the sibling `MPGram` repository next to this one, and the `mpgram` PyPI name is already reserved with dummy low-version package content.
- PyPI `miniproto` and crates.io `miniproto` are already reserved with dummy low-version package content; repository metadata and release tooling should assume those names are intentional, not accidental placeholders.
- `mpgram` must consume public `miniproto` APIs. It should not depend on private `miniproto._*` modules except for short-lived experiments before alpha.

## Future `mpgram` Work

- Start `mpgram` after the `miniproto` alpha API can authorize, invoke raw requests, persist sessions, generate raw schema classes, and consume basic updates.
- Put framework lifecycle, routers, nested routers, filters, command handling, middleware, dependency/context helpers, plugins, conversation/state helpers, bound message methods, and broad Telegram helper methods in `mpgram`.
- Keep `miniproto` focused on long-standing reliability problems in Python MTProto clients: memory leaks, disconnects, missed updates, timeouts, reconnect behavior, update gaps, and bounded resource use.

## Test Plan

- Unit tests: TL flags/vectors/primitives, constructor IDs, schema parser/generator golden files, crypto test vectors, msg_id/seq_no monotonicity, session encryption/redaction, RPC error mapping, peer cache behavior, and fallback parity between Python and Rust paths.
- Protocol tests: fake MTProto server for auth handshake, salt changes, ordinary and quick acks, containers, gzip, bad salt, bad msg, reconnect/resend token replacement, DC migration, flood wait, update gaps, duplicate suppression, and transport errors across all supported TCP modes.
- Media tests: chunk sizing, small vs big file paths, streamed uploads, retrying missing parts, download resume, ordered iterator backpressure/early close, per-DC scheduler caps/fairness/cancellation/isolation, optional plain hash corruption and interval validation, CDN redirect/decryption, progress callback ordering, and memory ceiling checks.
- Integration tests: optional Telegram test DC/live tests gated by `MINIPROTO_INTEGRATION=1`, credentials in environment only, covering sign-in, `get_me`, Saved Messages send, update receive, file upload/download, bot token auth, and reconnect.
- Performance acceptance: benchmark native vs fallback crypto, transport framing, generated hot and generic TL serialization, 1k pending RPCs, update dispatch latency, upload/download throughput, reconnect recovery, loop lag, and sustained RSS; publish raw distributions and baseline numbers in CI artifacts.
- Later performance acceptance: run common-task benchmark suites against well-known MTProto libraries, including Python libraries such as Telethon/Pyrogram/Hydrogram and at least one non-Python client implementation, so miniproto performance claims are backed by external comparisons instead of only native-vs-fallback deltas.
- Release acceptance: `uv run miniproto-release-check --offline --artifacts-dir .tmp/release-offline` is the canonical non-mutating aggregate for schema freshness, Ruff, ty, strict committed-reference and static-site documentation, pytest, Rust fmt/Clippy/tests, all nine non-live benchmark families, fresh wheel/sdist construction and inspection, clean isolated native import, and installed-console-script metadata. The manual **Build release artifacts** workflow then creates and attests one exact 24-wheel/one-sdist/one-crate candidate plus deterministic checksums/provenance; the separately permissioned **Publish release** workflow accepts only a verified build run ID, uses protected PyPI/crates.io OIDC publishers, populates a draft GitHub release, and makes it public only after both registries succeed. Individual commands remain documented diagnostics; credentialed live tests and matrices stay separately guarded.
- Tool CLI acceptance: every executable repository tool has a side-effect-free `--help` path and exactly one `[project.scripts]` entry. Source tests enforce the inventory, and clean-wheel acceptance invokes every installed console script with `--help` from outside the source checkout.
- Release-artifact automation acceptance: ordinary CI never builds wheels. The dispatch-only `.github/workflows/build-wheels.yml` builds and exercises normal CPython 3.13/3.14 and free-threaded CPython 3.14t across Linux glibc/musl x86_64 and aarch64/ARMv8 plus native Windows/macOS x86_64 and aarch64 runners, then adds the authoritative Python sdist and one isolated Cargo source package. Every lane installs the wheel with its declared `cryptography` and platform event-loop dependency, verifies the expected ABI and actual GIL state without injecting an unsupported GIL setting into normal interpreters, verifies concurrent native calls and protected string sessions, and runs every installed console script with `--help` from the selected interpreter's scripts directory; ordinary CI separately runs the 3.14t source/native acceptance with the same dependencies without producing wheel artifacts. CPython 3.13t is deliberately unsupported because dependency freshness takes precedence and current PyO3 no longer supports that ABI. ARMv7 is deliberately excluded because the Rust ARMv7 musl target has no published host tools and the Python dependency ecosystem has materially weaker 32-bit ARM wheel coverage.

## Assumptions

- Python remains the supported public language; Rust is used inside the package for speed, memory efficiency, and free-threaded readiness. The crates.io package currently exposes a `cdylib` named `miniproto_native` for Python and is published for source provenance; direct `use miniproto_native::...` support is deferred until a separately approved `rlib` and Rust-facing API contract exist. `cryptography` and the platform-appropriate `uvloop`/`winloop` backend are base dependencies and must remain compatible with supported normal and free-threaded interpreters; protected-session crypto selects native capabilities from benchmark evidence and falls back to cryptography when unavailable.
- MIT remains miniproto's license; Pyrogram-family GPL/LGPL projects, TgCrypto forks, and `@mtproto/core` are references only, not code sources.
- "Evergreen" means reproducible explicit schema refresh tooling, deterministic offline stale-generation CI, and scheduled/manual upstream reporting, not runtime schema fetching at import time.
- Pyroblack, Pyrofork, Kurigram, and Hydrogram validate the ergonomic shape, but v1 intentionally avoids a broad framework surface; raw API access covers unsupported features.
- TelegramPlayGround's Pyrogram repository is treated as a compiler/docs reference, not a runtime architecture reference.
- Default behavior is secure for server use: encrypted sessions, bounded queues, explicit retries, no secret logging, no implicit telemetry, and opt-in live tests.
