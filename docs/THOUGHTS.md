## 2026-06-30 — GPT 5.5 Extra High — Codex — "Create PROGRESS implementation plan"

- Unknown-size upload sources should stay treated as a disk-spooling problem, not an in-memory buffering problem: Telegram's big-file upload needs the total part count before `upload.saveBigFilePart`, so a truly streaming unknown-size source cannot safely choose the small/big method until it has been measured.
- Upload progress currently means accepted bytes after part-save success, not bytes read from the local source. With bounded concurrency, callback order should be monotonic in total accepted bytes, but not a guarantee that Telegram accepted part indexes in natural order.
- `send_file()` intentionally defaults to `inputMediaUploadedDocument`; automatic photo/video classification, thumbnail generation, albums, and rich media ergonomics are likely `mpgram` or later convenience work unless needed to prove protocol correctness.
- CDN coverage remains partly synthetic: unit tests can force `upload.fileCdnRedirect`, `upload.cdnFileReuploadNeeded`, and AES-CTR chunk decryption, but live Telegram tests may not naturally return a CDN redirect for small Saved Messages files. A future live gate may need either a large enough file, a known media fixture, or a controlled fake-server path to make CDN behavior deterministic.
- The current CDN primitive follows token/reupload/decrypt flow, but real CDN DC authorization and sender handoff are still a runtime integration risk; do not mistake local decrypt coverage for complete CDN production readiness.

## 2026-07-06 — GPT 5.5 Extra High — Codex — "Benchmarks ul/dl"

- Live media benchmark conclusions should keep their evidence scope attached: the useful measurements so far are mainly user-session DC4 runs from local/VPS environments, while bot runs and other DCs remain under-sampled. Treat defaults such as two upload lanes and one download lane as measured-good starting points, not protocol truths.
- Upload lanes appear useful up to a small number of independent senders because socket resets stop poisoning one huge in-flight batch, but lane count is not free: higher lane counts can add reconnect churn, sender rebuilds, retries, and noisier tails without improving total wall time.
- Download speed is still the uncomfortable gap. Raising download concurrency/lanes too aggressively caused flood waits, reconnect churn, and worse averages in observed runs; the fast reference behavior to study is likely not "more requests on the same shape" but better media transport scheduling, range sizing, request pacing, and connection reuse.
- Full-file downloads and random-access streaming want different defaults. Range cache and read-ahead are promising for repeated ranges, seek-heavy consumers, and media streaming, but they were harmful for one-shot sequential 2 GiB downloads when enabled blindly. Keep them opt-in or workload-detected until there is stronger evidence.
- Adaptive download chunk sizing is worth keeping visible in metrics. The sweet spot is probably DC-, account-, network-, file-, and time-dependent, so the algorithm should grow cautiously, settle when throughput regresses or flood waits increase, and avoid being bypassed by special sequential paths.
- The tail of large transfers deserves special attention: prior runs repeatedly lost a lot of average throughput near the end through timeouts, sender disconnects, or slow final retries. Benchmark summaries should separate steady-state throughput from tail penalty so a good transport core is not hidden by finalization/retry behavior.
- GitHub Actions live benchmarks are useful as a smoke/regression signal but not as an absolute throughput reference; hosted runner network behavior was much worse than local/VPS measurements. CI should keep artifacts/logs/JSON, but performance comparisons should prefer controlled VPS/local matrices.
- Operation-specific names matter for benchmark knobs and env vars. Upload and download should keep separate option names even when they share concepts like lanes, concurrency, request timeout, part size, byte window, or read-ahead, because the favorable values diverge sharply.
- A reusable miniproto file ID should be an SDK-level transport handle, not a Pyrogram-compatible promise. It should encode enough to reconstruct the correct `InputDocument`/`InputPhoto`-style reference later, including media kind, id/access hash, file reference, dc id, size, and relevant attributes, while accepting that file references can expire and need refresh.
- File ID support must not silently collapse all media into "document". Telegram-facing user concepts include photos, videos, GIF/animation, audio, voice notes, round videos, stickers, thumbnails, and plain documents; even if upload defaults stay document-first, the ID format needs room for the broader media taxonomy.
- Peer resolution should learn from failures. Numeric bot peer IDs can fail when the access hash is not known, while usernames or cached dialogs can work; the library can opportunistically resolve/cache peers after access-hash-related errors, but it should keep clear logs so callers understand when a retry changed lookup strategy.
- RSS/memory telemetry needs explicit degradation semantics. If resident memory cannot be read on a platform/runtime, report the metric as unavailable with a reason instead of leaving ambiguous `None` values in final summaries.

Bench counters do not record the error template string, so these cannot be distinguished today; log the template before drawing post-fix conclusions — if it is premium-wait, it will survive the ack fix and _is_ the server ceiling mechanism.

Upload `lanes=auto(8)` hit 16.24 MiB/s while an outwardly identical explicit `lanes=8` run got 10.98 with 130 reconnects + 1332 retries — same nominal shape, wildly different outcome, most plausibly ack-kill timing variance. A perfect single-connection sequential client cannot beat that; the gap is structural (pipelining), not per-request overhead. The bench should measure raw small-RPC RTT so network vs implementation contributions stay separable in future comparisons.
- The ~16.5 MiB/s cluster at the top of libspeed.telegram.tools looks like a server-side per-transfer/account cap (radically different client designs all landing there), but that is inference — GitHub-runner egress shaping could contribute. Comparison confounds to keep attached to any published number: libspeed = bots on DC1 from US runners, several harnesses exclude `sendMedia` finalize from the upload window, most download to RAM; miniproto samples = user on DC4 from a EU VPS writing to disk. Use `transfer_duration` and add a bot-DC1 mode for apples-to-apples claims.
- Could not verify from the benchmark JSONs whether the VPS runs had the Rust extension loaded; nothing records `native_available`. The 16.24 MiB/s upload run argues native was active (pure-Python per-16-byte-block IGE would likely cap lower), but that is a guess — the silent-fallback risk is why the plan demands a loud native check before trusting any perf number.
- PyO3 + `panic = "abort"` in the workspace release profile: PyO3 normally converts Rust panics into Python exceptions via unwinding; with abort, any native panic kills the entire host process. For a library embedded in user servers this is a robustness decision that deserves an explicit choice, not a leftover. Also `incremental = true` alongside `lto = "fat"` is dead weight — cargo disables incremental under LTO.
- Correction to my own plan (TASK-P0-4 sub-bullet): re-reading `drop_sender(expected=...)`, when the tracked sender differs from `expected`, the tracked one survives and only the caller's stale reference is disconnected — likely harmless orphan cleanup rather than the lane-killing race the plan implies. The misleading part is the `sender_drop_skipped` metric name (it "skips" yet still disconnects the stale object). Verify intent during implementation; the headline P0-4 claim (whole-connection drop on per-request timeout) stands regardless.
- `bytes(data)` wraps in `tl/codec.py` are free today because callers pass `bytes` (CPython returns the same object), but the moment memoryviews get threaded through decode (TASK-CPU-3), every primitive read silently becomes a full-buffer copy — O(n²) on big payloads. Remove the defensive wraps as part of that task, not after it regresses.
- Undocumented server folklore worth preserving but not blindly trusting: mtcute refuses to pack more than one `upload.getFile` per msg_container because more "seems to cause flood_wait" (source comment, not docs); MTKruto negates the DC ID when exporting authorization for media clients. Treat both as folklore to verify on fake-server/live, but do not casually violate the container rule when implementing outgoing containers.
- `invokeWithoutUpdates` on media lanes does not mean "nothing unsolicited": `new_session_created`, bad salt/msg notifications, and other service messages still arrive and still need acking and handling. The bounded-incoming-queue work applies to media lanes too.
- Session-ID reuse across process restarts (persisted `session_id` metadata + reset seq counters) is an open question: server tolerance for a reused session_id with restarting seq_no is untested here, and most references generate fresh IDs per connect. Fresh-per-connect is the safer default but changes `new_session_created`/salt frequency — verify on the fake server before switching, and decide what "session" means for miniproto persistence.
- Telegram app-config limits (`small_queue_max_active_operations_count`, `large_queue_max_active_operations_count`, `upload_max_fileparts_*`) cap parallel _files_ per DC, not parts-per-file, and miniproto never reads app config. A server SDK running many simultaneous transfers will hit those before per-transfer tuning matters; that is also the natural home for the shared per-DC byte-weighted scheduler idea from the 2026-07-03 notes.
- Adaptive part sizing verdict is inconclusive: the c1 adaptive run (5.33/4.78 MiB/s across repeats) vs baseline (4.98/4.85) differs by less than run-to-run variance, and `adaptive_part_size_changes: 1` suggests one 512K→1M growth then settle. Re-measure after the ack fix. Separately, nothing validates that a user-supplied `part_size` is a power-of-two divisor of 1 MiB — the doubling growth silently assumes it, and Telegram rejects illegal limits.
- Read-ahead run counters conflate main-path and prefetch-task errors (prefetch fetches run the same retry path and increment the same counters), so the "634 flood waits" figure cannot be attributed cleanly. Tag counters by origin (window vs prefetch) when fixing read-ahead, or the next A/B will be unreadable too.
- All performance evidence is Linux/uvloop; Windows (winloop/Proactor) is unsampled — TCP_NODELAY defaults, `to_thread` costs, and IOCP read patterns all differ, and the primary dev machine is Windows. Expect local numbers to diverge from VPS numbers for reasons unrelated to code changes.

## 2026-07-07 — Claude Fable 5 Max — Zed — "P0/P1 wave + live flood-pacing findings"

- `FLOOD_PREMIUM_WAIT` confirmed as the user-account download limiter (resolves the 2026-07-06 suspicion): in two directly comparable `both` runs (same c6/l2, same DC4, download hot after upload), user stdout showed many premium waits while the bot run had zero — and the bot downloaded +60% faster (5.33 vs 3.33 MiB/s) with far smoother samples (stdev 0.62 vs 1.81). Non-premium user download speed is product policy; no client change moves it. Any published download number must carry the account tier.
- There is a second, separate cap that hits bots too: generic `upload.getFile` request pacing. Sustained `requests_per_s` converged regardless of concurrency (user ~6.3–6.8 at c4/c6/c8, bot ~8.0) while the flood RATE scaled with concurrency (36% → 53% → 69% of parts) and throughput ordered c4 (4.60) > c6 (4.32) > c8 (4.00 MiB/s). Concurrency above the budget converts allowance into stalls, not speed. p95 pinned at ~6.2–6.4 MiB/s in every run, user and bot alike — either the true DC4 per-transfer budget or the coincidence of 1 MiB parts × ~6.3 req/s; c8 bursting to 8.16 proves the client pipeline can exceed it when the server allows. `byte_window_waits == 0` everywhere: the 8 MiB window never binds at ≤8×1 MiB, it is not the limiter.
- Budget asymmetry on the same account/DC/session: `saveBigFilePart` sustains ~35 req/s at ~6.5% flood rate (16.3 MiB/s uploads for BOTH actors), `getFile` gets ~7 req/s. Upload tuning intuitions do not transfer to downloads.
- The original P1-3 design (flood-sleeping tasks release slot+bytes, scheduler backfills) is a positive-feedback amplifier under rate-based pacing and was falsified live in a single run: six `FLOOD_WAIT_2` within 50 ms → backfill sustained the request rate → escalation to 10–15 s waits, 8161 retries by the 37 MiB mark, then a retry-budget abort. Meta-lesson: the acceptance test validated the harmful behavior perfectly — fake servers cannot express server-side pacing policy, so "plan-prescribed + unit-tested" still needs one live falsification run before becoming a default.
- Hot-account contamination: a download started right after a flood-heavy 2 GiB upload runs ~25–30% slower with longer waits (user avg flood 2.53 s hot vs 1.77 s cold). The download phase of `--operation both` is not comparable to standalone runs; label which kind any number came from. A standalone bot download remains unsampled — it is the missing datapoint for the DC4-vs-DC1 (libspeed 16.4) question.
- Self-inflicted over-sleep, quantified: the 1 s flood-sleep floor + 0–1 s jitter adds `retry_sleep − flood_wait` ≈ 520–700 s per flood-capped run (~1000 floods). The de-synchronization is necessary (lockstep retries re-flood; observed), but the constants are generous; candidate tightening: floor only when `seconds == 0`, jitter ≤ 0.3 s. Deliberately untouched until the pacing decision below.
- Parking lot, next lever: flood-aware LAUNCH pacing — a token bucket targeting ~90% of the recently observed successful request rate, leaving slots/window untouched. It converts ~1000 stalls into smooth flow at the allowed rate (estimated +30–45% for both account tiers) and is inert for uncapped accounts. Notably it is neither of the two throttle options originally offered (gentle-reduce vs never-reduce); the live data converged on a third shape: fixed concurrency, adaptive rate. Related bench gap: counters do not record flood error NAMES (premium vs plain) — add the distribution so this never needs stdout grepping again. Only revisit the c6 download default after standalone bot data; bots may still want it.
- Under a REQUEST-rate cap, bigger parts are strictly better (6 req/s × 1 MiB beats 6 req/s × 512 KiB); the adaptive sizer grew to 1 MiB in every live run, which is the right call IF the cap is request-based — but a 512K-vs-1M A/B under the post-P0 regime never ran, and if the cap is byte-based the sizer is fighting for nothing.
- Plan acceptance criteria staleness: "upload retries < 50" predates the flood-budget redesign. Flood retries now ARE the pacing mechanism — 276–376 per ceiling-grade 16.3 MiB/s upload, all benign. `part_retries ≈ flood_waits` is health, not failure; audit counters, not the old thresholds.
- Receive-loop double-read race mechanics (fix in sender via task-identity check; timing preserved here): `writer.close()` flips `is_closing()` immediately but does NOT synchronously wake a blocked `readexactly` on all event loops. So `connect()` can observe is_connected == False and spawn a replacement receive loop while the OLD loop still holds a pending read; when that read finally raises, the old loop re-reads `self._transport` — now the replacement — and two coroutines read one StreamReader (RuntimeError). Pattern: any owner-loop awaiting shared transport state must re-verify ownership after EVERY recovery await. The race was latent before the idle watchdog; faster timeout cycling exposed it.
- Fake-server asymmetry (intentional, will trip someone): client-sent msg_containers are unwrapped and MsgsAck items are recorded on `acks_received` WITHOUT reaching the handler, while top-level MsgsAck frames still dispatch to handlers (the standalone-flush tests rely on that). Tests asserting ack arrival must know which path they exercise.
- Cross-DC (P1-5) live-unverified list: FILE_MIGRATE redirect, exported-auth import on media lanes, per-DC key persistence (`dc_auth` metadata), and the AUTH_KEY_UNREGISTERED→rebuild path are all fake-tested only — no live run ever touched a cross-DC file. MTKruto's negated-DC-ID export folklore was NOT adopted (plain `exportAuthorization(dc_id)`, Telethon-style); if cross-DC misbehaves live, check that folklore first. Authorization import runs per lane build (idempotent, costs 1 RTT) instead of once per auth key — deliberate simplicity while lane builds are rare; revisit if builds ever churn again.
- The per-part flood retry cap (16) is invented, not reference behavior — mtcute/Pyrogram sleep media floods indefinitely. It honors the "no unlimited waits" decision while surviving realistic streaks (worst case 16 × ≤30 s = 8 min/part). If `flood_retry_budget_exhausted` ever fires live, that is the knob to question.
- Counter-scoping quirk: in `both` runs the download row shows `media_lane_drops: 2` — that is the UPLOAD pool idle-closing 120 s into the download phase. Counters are process-cumulative snapshots per phase, not per-operation scoped; future counter-diffing will misattribute cross-phase events like this.
- Tooling notes: fuzzy-match file editing reliably fails on this repo's long unicode-heavy markdown lines (master plan, media.md) — scripted `str.replace` via a temp Python file is the dependable path. GitHub Actions dispatch forms remember previously typed inputs, so updated workflow input defaults never reach anyone who dispatched before. And defaults now live in four layers (library, bench script, `.env`/`.env.example`, CI workflow inputs) that drift unless changed together — this wave touched all four on purpose.

## 2026-07-09 — GPT 5.5 Extra High — Codex — "Finish Fable 5 fixes"

- Abridged transport error-frame parsing is a footgun. A real negative transport frame can begin with the same byte that abridged mode normally treats as a short length, but encrypted payload bytes are effectively random; combining the length byte with the first three payload bytes caused normal live packets to sometimes look like negative errors. Fake tests that only feed `-429` are not enough — include a normal abridged packet whose first encrypted payload bytes would be negative if misparsed. This exact mistake passed focused tests and only surfaced as live `connection retry limit exceeded`.
- Quick-ack should stay out of behavior until the frame shape is decoded with the same caution as negative transport errors. A parser that speculatively peeks into payload bytes can corrupt normal encrypted traffic; quick-ack needs explicit transport framing tests, fake-server coverage, and one live trace before it becomes more than a documented future hook.
- Fresh session IDs per sender connection are safer than persisting a session ID with reset seq counters, but this deliberately means more `new_session_created` churn is possible after reconnects/restarts. Treat increased session-created service messages as expected unless it correlates with bad-msg storms, salt churn, or missed responses.
- `AUTH_KEY_DUPLICATED` should not be lumped into generic auth-key invalidation. Dropping the current sender is cheap; clearing a durable auth key because one lane tripped a duplicate-session edge would be a destructive recovery path. Keep the distinction sharp in future error-classification edits.
- `msgs_state_req` handling is intentionally minimal: the sender replies with a byte per requested message so the server is not ignored, but it does not maintain a rich historical state table. `msg_resend_req` only resends still-pending messages; anything already completed or evicted is not replayable today. If server-side state recovery becomes important, add a bounded outgoing-message history rather than pretending the current pending map is full protocol memory.
- Per-channel update recovery depends on having a full channel access hash. Min entities are useful for display and update context but should not poison the peer cache with unusable hashes; when only a min channel is known, it is better to leave a channel gap unrecovered/noisy than to fabricate an `InputChannel` that will fail later.
- Message-backed file-reference refresh is only automatic when the caller supplies enough provenance: a raw `Message` or `Media.raw` carrying that message. A standalone miniproto file ID can still contain an expired file reference with no way to rediscover the source message. Future richer file IDs may need optional message-peer/message-id provenance if automatic refresh from opaque IDs becomes a goal.
- Retryability is method-specific, not transport-specific. `messages.sendMessage` and `messages.sendMedia` are safe to retry because `random_id` gives Telegram dedupe semantics; that reasoning does not automatically apply to edits, deletes, read markers, or arbitrary content-related RPCs.
- Split encrypted SQLite domains cut write amplification, but the compatibility contract matters: arbitrary legacy mapping payloads still round-trip through a generic payload domain, while typed `SessionRecord` gets auth/peers/update/metadata domains. Future migrations should preserve that exact-map escape hatch until a deliberate storage-version bump removes it.
- Upload part ceilings are not just a constant. The historical 4000-part default remains the conservative SDK fallback, but premium/server-side app config can raise it. Growing a too-small caller `part_size` toward 512 KiB is a convenience, not a license to accept arbitrary part geometry; Telegram alignment and part-count legality still need to be validated before upload starts.
- Live integration tests acted as an encrypted-traffic parser fuzzer in this wave. The ordinary unit suite passed before the abridged parser fix, but live auth/message/media calls all failed with the same reconnect-limit symptom. When a transport parser changes, keep one live smoke run in the verification matrix if credentials are available; otherwise explicitly mark the gap.

## 2026-07-09 - EDM115 - "Download speed improvements"

Currently, uploads are -/+ on-par with top libs but downloads are 3x worst.  
Before I can actually come up with a fix for that, I had an idea.  
Every user can open multiple sessions, right ? (ex phone and laptop). Bots too afaik.  
Wouldn't it be possible to just split the download across multiple sessions ? The sole requirements is to see if FloodWait's are correlated to a session or account, and to which degree (ex being rate-limited on session1 doesn't auto rate-limit you on session2 but increases your likelihood so you don't just open 400 sessions at once).  
Since we download a file in chunks, we could just create a pool of multiple sessions (workers). We would need to check first the file size, for ex a file < 100 MiB might not require more than 1 session but a 2 GiB might benefit from 4, idk.  
Then, we have the queue of all chunks. Let's say we have 3 sessions in the pool. We split equally the chunks to all 3 sessions. There's actually 2 sub-queues : one that is the worker's immediate pool that it can grab into, containing let's say 25 chunks, and a secondary pool with the rest of its work, planned for later. We would also need to know if requesting non-contiguous chunks is worst in perf than same-block chunks (read : do we randomize the queue or keep it sorted).  
Then, there's an orchestrator that distributes the content of the secondary queue into the worker's primary queues as they ingest and complete work. It monitors for FloodWait's and pauses the primary queue ingestion when a worker encounters it, and moves parts of its secondary queue equally to other's secondary queues to level the work time across all workers.
When worker2 have no more work left in the secondary queue and worker1 is in rate-limit, any task of worker1's secondary queue can be split equally by time it'll take on other worker's secondary queues. If worker2 have no more tasks at all, it can ingest remaining tasks from all other queues given that it doesn't perform worse than potential non-contiguous blocks penalties.  
Uploads will probably never benefit from this as I don't believe you can upload chunks of the same file from multiple sessions.  
This behavior wouldn't be the default but rather an option that users can toggle on or not.

## 2026-07-09 - GPT-5.6 Sol Max - Codex - "Download speed improvements feasibility"

- Same-auth-key multi-session downloads are already the current miniproto shape, not a missing novel lever: `Client.download_media()` defaults to `media_lanes=2` and `concurrency=6`, each media lane builds a fresh sender session ID, and refs checked here (mtcute 2x3, MTKruto 2x2, grammers 4 workers, gotd `WithThreads(6)`) all split one file across concurrent `upload.getFile` requests.
- The unproven/risky variant is multiple independent permanent auth keys/device sessions for one actor. Telegram docs and live notes both point at account-tier/method/DC pacing (`FLOOD_PREMIUM_WAIT`, generic `upload.getFile` budgets), so treat it as a benchmark-only experiment with pre-existing session files and hard caps, not public API/default behavior.
- Recommended next lever stays measurement-first pacing: record flood error names per worker/session, standalone bot/user cold downloads, 512 KiB vs 1 MiB under post-fix conditions, and only then test multi-client auth-key sharding for scaling.
- Implemented the experiment as `tools/bench/benchmark_multi_session_download.py` with a second explicit guard (`MINIPROTO_MULTI_SESSION_DOWNLOAD_BENCH=1` plus `MINIPROTO_LIVE_BENCH=1`), contiguous 1 MiB-aligned shard planning, per-session default `concurrency=1`/`media_lanes=1` to isolate auth-key scaling, duplicate auth-key detection that aborts by default, aggregate flood counters, JSON output, optional assembly, and offline tests in `tests/test_multi_session_download_benchmark.py`.
- First VPS user result falsifies the useful version of auth-key sharding: two distinct auth keys for the same user on DC4 downloaded 2000 MiB at only 4.59 MiB/s transfer / 4.57 MiB/s overall, with workers at 2.47 and 2.30 MiB/s, 52 `FloodPremiumWait` + 32 generic `FloodWait`, and 467/535 flood-wait seconds from premium waits. Upload immediately before was healthy at 15.5 MiB/s, and there were zero reconnects/sender drops/byte-window waits, so this points to account-tier download pacing shared across auth keys, not a local transport bottleneck.
- First VPS bot result is meaningfully different: 2 distinct bot auth keys reached 10.39 MiB/s transfer, 4 reached 16.93 MiB/s, and 8 fell back to 15.94 MiB/s, with zero `FloodPremiumWait` in all bot runs. 4 workers looks like the current sweet spot; 8 generated 445 generic floods / 600 flood seconds and 4413 part requests, so it likely overdrives `upload.getFile` pacing and may also be hurt by adaptive part sizing settling noisily under contention. Treat bot auth-key sharding as plausibly useful but capped; next confirmation should be repeated 1/2/4/6/8 bot runs with fixed 1 MiB parts plus a normal single-client bot baseline.
- The size matrix confirmed a practical bot-only policy: c1 through 50 MiB, c2 through 250 MiB, and c4 above 250 MiB. c4 remained near the observed ~16 MiB/s ceiling while c6/c8 added floods without useful throughput, so the public option should stay capped at four independent auth keys rather than exposing arbitrary worker counts.
- The implemented lifecycle is deliberately lazy and persistent. A bot starts with only its primary session; a 5 MiB download creates nothing, a later 75 MiB download creates only `download-1`, and a later 2 GiB download creates only the still-missing `download-2` and `download-3`. Auxiliary clients disconnect after each transfer while their consistently named sibling session storage remains available across later downloads and process restarts.
- Auxiliary auth keys are independent bot authorizations, not cloned primary keys. Creating a missing auxiliary therefore requires the bot token: a token passed to `sign_in_bot()` is retained only for that client lifetime, while `ClientConfig.bot_token` is needed when a restarted process may need to create auxiliaries that do not exist yet. Existing authorized auxiliary session files can be reused without the token, and the token is never persisted or included in config `repr`.
- Only the primary client owns update handling. Auxiliary clients do not start `UpdateManager`, do not start receive dispatch, initialize under `invokeWithoutUpdates`, and exist solely for their assigned contiguous download range. User accounts, unknown-size/range/resume downloads, missing sibling-storage support, or failed auxiliary authorization log an error and degrade to the best available c1/c2 path instead of making the download option a hard failure.

## 2026-07-16 — GPT-5.6 Sol Ultra — Codex — "Improvements part 1"

- Legacy single-envelope migration has two different notions of change: all typed domain rows may need a physical first write, but `domain_revisions()` must advance only for logical plaintext differences. Keep a separate legacy/forced-write flag instead of representing a typed legacy record as the `payload` domain, or a peer-only mutation incorrectly invalidates auth/update/metadata and payload consumers.
- `Client.disconnect()` closes its session storage. With the new fail-after-close contract, tests or applications that want to reconnect must reopen durable storage or construct a fresh in-memory backend from a pre-close snapshot; reusing the same closed `InMemorySessionStorage` is intentionally invalid.
- On this Windows checkout, pytest's default `%LOCALAPPDATA%\Temp\pytest-of-*` root can fail with `WinError 5` even when the command is elevated. Use a unique workspace-local child under `.pytest-tmp/<plan>/`; pytest does not create a missing nested `--basetemp` parent, so create the plan parent first. Remove only directories created by the current task because parallel agents may own neighboring roots.
- Cancellation around `asyncio.to_thread()` storage work is not atomic merely because the Python coroutine was cancelled. If a backend call may already be running under the storage cache lock, shield and join it, reconcile the cache/revision/closed state after the backend actually finishes, and only then re-raise the original cancellation; otherwise callers can observe a stale cache after a committed write or a half-closed storage object.
- A first untrusted inbound `msg_container` needs a provisional time offset derived from the outer envelope. Validating all children while `time_trusted` is still false skips their time windows, while committing the outer first breaks atomic rejection. Validate the outer's non-time invariants, validate every child against the provisional offset and a provisional replay set, and commit nothing until the whole container passes.
- Windows import/codec microbenchmarks can be badly confounded by native-versus-fallback execution, subprocess startup, scheduler variance, and roughly 15.625 ms process-time quantization. For plan-owned warmed-path comparisons, use the same process, identical class/native state, interleaved old/new rounds, and a workload long enough to dominate the clock quantum; keep startup and retained-memory measurements as separate gates.

## 2026-07-17 — GPT-5.6 Sol Ultra — Codex — "Improvements part 2"

- Encrypted-envelope validation order is itself part of the security contract: authenticate `msg_key` before returning a semantic `auth_key_id` failure, consistently in native and fallback paths, so malformed headers cannot create a distinguishable shortcut. A receive-loop validation failure should close/fatal the transport without eagerly deleting pending futures or aliases; the request coroutine, timeout, cancellation, or disconnect path still owns that cleanup.
- Pending-RPC capacity must be reserved synchronously before the caller's first await, and exactly one request coroutine must own release. Internal service traffic needs an uncounted path, while user-supplied metric sinks must be best-effort so a raising sink cannot leak a slot or replace the protocol result; propagated `BaseException` during reservation still requires rollback.
- Incremental peer indexes cannot derive canonical conflict order from sets or final-state diffs alone. Same-key `self`/`user` transitions and remove-then-reinsert batches need explicit ordered merge metadata that distinguishes stable replacement, removal, and append. Warm-path benchmarks must count calls at the `_CachedSessionStorage.load()` boundary and preserve username TTL semantics; counting only backend loads can falsely prove a no-copy cache.
- `docs/raw-api.md` is generator-owned by `tools/schema/generate.py::_render_docs`; freshness fixes belong in the renderer plus a regression and regeneration, never only in the generated page. Generated facade stubs also legitimately inherit Telegram's naming, so lint exceptions should remain exact-file/exact-rule rather than broad repository ignores.
- On Windows, PyO3 Rust tests need uv's CPython directory on `PATH` so `python314.dll` can be loaded. Long RTK-wrapped pytest commands may outlive the command wrapper and temporarily lock `_native.cp314-win_amd64.pyd`; certify completion from the real exit/JUnit artifact, and use a module-only lock-owner query before considering termination rather than enumerating unrelated process arguments.
